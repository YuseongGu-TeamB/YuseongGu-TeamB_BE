# 프런트 요구사항 (시연용 / apps/desktop — Electron + React + TypeScript)

## 0. 목표와 범위
- 담당자가 **민원을 붙여넣고 → 답변 후보를 보고 → 하나를 골라 수정 → 전송**하는 흐름이 끝까지 도는 것. 목표는 시연 성공.
- 디자인은 **KRDS(대한민국 정부 디자인 시스템)만 따른다.** 별도 디자인 시안은 없다.
- 백엔드(`apps/api`)와 계약(`packages/contracts`)은 이미 있다. 계약 타입은 반드시 `packages/contracts`에서 import한다.
- 범위 밖: 로그인, 민원 목록/검색, 설정 화면, 개발자 시드 API(`/dev/*`) 호출, 다국어, 자동 업데이트, 설치 패키지 서명.

## 1. 기술 선택
- Electron + Vite + React + TypeScript (electron-vite 등 단순한 템플릿 하나).
- 스타일: npm `krds-uiux`의 CSS·토큰을 그대로 쓴다. **추가 UI 라이브러리(MUI, Tailwind, shadcn 등) 쓰지 않는다.**
- 상태 관리: React 기본(useState/useReducer). 서버 상태 라이브러리는 필요하면 TanStack Query 하나만.
- API 주소: `VITE_API_BASE_URL`(기본 `http://localhost:3000`).
- Electron 보안 기본값: `contextIsolation: true`, `nodeIntegration: false`, `sandbox: true`. 렌더러는 HTTP로만 API를 호출한다(IPC로 백엔드 기능을 우회하지 않는다).

## 2. KRDS 적용 규칙
- 컴포넌트를 만들기 전에 `node_modules/krds-uiux` 안의 해당 컴포넌트 **마크업과 클래스명을 먼저 확인**하고 그대로 쓴다. 클래스명을 지어내지 않는다.
- 임의 CSS는 레이아웃(그리드, 여백) 정도로 최소화하고, 값은 KRDS 토큰(CSS 변수)만 쓴다. 색·글꼴 크기를 하드코딩하지 않는다.
- 쓸 컴포넌트는 이 정도로 충분하다: 텍스트 영역, 버튼, 카드(또는 박스), 배지/태그, 알림(경고·오류·정보), 단계 표시(스텝 인디케이터), 모달(확인 대화상자), 스피너.
- 폰트·아이콘 등 리소스는 **로컬에 번들**한다. 외부 CDN·웹폰트 호출 금지(오프라인 시연).
- 접근성: 모든 입력에 label, 키보드만으로 전체 흐름 가능, 포커스 표시 유지, 진행 상태는 `aria-live`로 읽히게.

## 3. 화면 (창 하나, 단계형 3화면 + 완료)
상단에 단계 표시(① 민원 입력 → ② 후보 선택 → ③ 수정·전송)를 둔다.

### 화면 ① 민원 입력
- 큰 텍스트 영역 하나(민원 원문 붙여넣기). 글자 수 표시, 최대 길이는 백엔드 `COMPLAINT_MAX_CHARS`와 맞춘다(기본 5000).
- "답변 후보 만들기" 버튼 → `POST /complaints/quick` → `202 { complaint_id, run_id }`.
- 바로 `GET /complaints/:id/progress`(SSE) 구독 → **진행 목록**을 보여준다:
  유사 답변 검색 → 민원 분석 → 근거·접근 유형 결정 → 후보 작성(접근 유형별로 완료/실패 표시).
- `done` 이벤트를 받으면 화면 ②로. `error` 이벤트면 오류 알림 + "다시 시도" 버튼.
- SSE 연결이 끊기면 재연결(서버가 지난 이벤트를 다시 보내 준다). 그래도 안 되면 `GET /complaints/:id`로 결과를 확인한다.

### 화면 ② 후보 선택
- 화면 왼쪽(또는 위)에 **민원 원문**을 항상 보여준다.
- `is_info_sufficient === false`면 상단에 경고 알림: "정보가 부족할 수 있습니다: {insufficient_reason}".
- 후보마다 카드 하나:
  - 접근 유형 배지(한국어 라벨: 절차 안내 중심 / 현장 확인 일정 제시 / 즉시 조치 안내 / 요건 미충족 안내)
  - 답변 본문(`answer`)
  - **근거**: `used_sources`의 각 source에 대해 근거 원문을 펼쳐 볼 수 있게(아래 4번의 `evidence` 사용). 근거가 없으면 "근거 없음" 표시.
  - **검토 필요**: `assumptions`가 있으면 경고 스타일로 목록 표시("근거 없이 들어간 내용").
  - "이 답변 선택" 버튼 → `PATCH /drafts/:id { selected: true }` 후 화면 ③.
- 생성에 실패한 후보(`failed`)는 회색 카드로 "생성 실패: {reason}"만 표시.
- "후보 다시 만들기" 버튼 → `POST /complaints/:id/generate` → 화면 ①과 같은 진행 표시 → 새 후보로 교체.

### 화면 ③ 수정·전송
- 선택한 답변을 텍스트 영역에서 수정. 원문 민원과 근거는 옆에 계속 표시.
- 수정 내용은 입력을 멈춘 뒤 자동 저장(`PATCH /drafts/:id { edited_answer }`, 디바운스 1초) + "저장됨" 표시.
- "다른 후보 고르기" 버튼 → 화면 ②로(선택 해제).
- "전송" 버튼 → **확인 모달**("이 답변을 승인하고 전송합니다. 전송된 답변은 이후 답변 작성의 근거로 쓰입니다.")
  → 확인 시 `POST /complaints/:id/approve` → `POST /complaints/:id/send` 순서로 호출.
  - approve 성공 후 send가 실패하면 "승인됨, 전송 실패" 상태를 보여주고 "전송 다시 시도"(send만 재호출)를 제공한다.

### 완료 화면
- "전송되었습니다" + 최종 답변 본문 + "새 민원 입력" 버튼(화면 ①로, 상태 초기화).

## 4. 백엔드에 필요한 작은 추가 (계약 변경 아님)
- 근거 원문을 보여주려면 검색 결과가 필요하다. `GenerateApiResponse` **봉투**와 `GET /complaints/:id`에
  `evidence: { source: string; content: string }[]`(그 실행에서 쓴 검색 결과)를 추가한다. 계약 타입(`Candidate`, `GenerateResponse`)은 바꾸지 않는다.
- 이 외에 백엔드 변경이 필요하면 만들기 전에 먼저 묻는다.

## 5. 상단 상태 표시 (시연용)
- 헤더 오른쪽에 `GET /health` 결과를 작은 배지로: DB · 임베딩 · LLM 각각 "로컬"/"외부" + 연결 상태.
  "검색·저장은 이 PC에서 로컬로 돈다"를 시연에서 보여주는 용도. 30초마다 갱신.

## 6. 오류와 빈 상태
- API 오류는 백엔드가 주는 한국어 메시지를 그대로 알림에 보여준다. 기술적인 스택이나 원문 민원을 화면·콘솔에 남기지 않는다.
- 생성 중에는 같은 버튼을 중복으로 누를 수 없게 한다(백엔드도 409를 준다).
- 후보가 0개면 "후보를 만들지 못했습니다" + "다시 만들기".

## 7. 하지 말 것
- 계약 타입을 프런트에서 다시 정의하지 말 것(`packages/contracts`만 import).
- KRDS에 없는 클래스명을 만들거나 다른 UI 라이브러리를 추가하지 말 것.
- 요구사항에 없는 화면·기능(목록, 통계, 설정, 다크 모드 등)을 만들지 말 것.
- 외부 네트워크(CDN, 웹폰트, 분석 스크립트) 호출 금지.

## 8. 작업 순서와 완료 기준
1. `apps/desktop` 뼈대 + KRDS CSS 적용 + 빈 3화면 이동 → **먼저 계획을 보여주고 확인받은 뒤 시작.**
2. 화면 ①: quick 호출 + SSE 진행 표시.
3. 화면 ②: 후보 카드, 근거·검토 필요 표시, 재생성 (+ 4번 백엔드 추가).
4. 화면 ③ + 완료 화면: 수정 자동 저장, 승인·전송.
5. 헤더 상태 배지, 오류 처리 다듬기, README에 실행 방법 추가.
- 각 단계가 끝나면 실행 화면 스크린샷이나 짧은 설명으로 보고한다.
- **완료 기준**: 백엔드와 데스크톱을 띄운 상태에서 "붙여넣기 → 후보 → 선택·수정 → 전송 → 새 민원"을 끝까지 한 번 성공.
  같은 내용의 민원을 다시 넣으면 방금 전송한 답변이 근거로 보인다(피드백 루프 확인).
